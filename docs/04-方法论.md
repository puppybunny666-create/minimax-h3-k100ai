# 04-方法论：对拍、判别实验与证据纪律

> 这两个月最大的产出不是某个修复，而是一套在"没有参考实现"的平台上做数值验证
> 和排障的打法。核心原则一句话：**永远要有一个不受待测系统污染的参照系。**

## 一、算子对拍：参照系三层分层

国产算力跑大模型，真正的成本不在"跑不起来"——总有 workaround——而在
**"跑起来了但结果是错的"**：不崩、不 NaN、日志全绿，只有人眼（或判别实验）能看出来。
解药是三层参照系：

| 层 | 参照物 | 做法 |
|---|---|---|
| 算子级 | 手写朴素实现 | RMSNorm / attention / 调制链全部用纯 torch 重写，与平台 kernel 逐位对拍 |
| 模块级 | checkpoint 权重 + 离线复现 | 从 safetensors 直接加载，CPU/单卡复算整条链，与运行时逐张量比对 |
| 系统级 | 扰动响应 | 换 prompt / 换 seed / 换精度，看输出的差分是否合理 |

灰暗糊战役的转折点正是第 2 层：**所有系统内自洽的验证都绿灯，只有引入
"checkpoint + 手写链"这个外部参照才撕开缺口。**

反面教训必须写明：灰暗糊期间所有逐位验证全绿——因为验证用例和被测代码用的是
**同一份错权重**（oracle 拿 raw 对 raw，错的俩一致）。**"自洽"不是"正确"。**

实操扩展示例（权重对拍覆盖面）：qkv / mlp / out_proj / adaln（含 bias）逐参数
checkpoint 对拍，目标 `max_diff = 0`（逐位）；任何非零即是线索。

## 二、判别实验设计

每个假设配一个"一发定生死"的实验，**事先写好两种结果的解读**：

| 假设 | 判别实验 | 高值含义 | 低值含义 |
|---|---|---|---|
| 条件链路死了 | 同 seed 换 prompt，比对最终 latent 余弦 | >0.99 条件死 | <0.5 条件活 |
| bf16 累积失真 | 残差流全程 FP32 重跑 | 与 bf16 有差 → 精度问题 | 分毫不差 → 精度无罪 |
| 运行时用的是哪份权重 | 手写离线复现"重排/不重排"两变体 | 哪个匹配运行时，运行时用的就是哪个 | — |
| 时间嵌入坏了 | 从 checkpoint 离线复算 t_emb 对拍 | cos 低 → 坏 | cos≈1 → 排除 |

灰暗糊破案的四步全是判别实验。**统计是听诊器，判别实验是活检**——范数、std、熵
这些"看一眼统计"只能排除不能定罪。

画面类问题同样有数值判据（不必人眼）：

- 灰暗糊：像素 std=9.4（正常 50–70），帧间相关 0.41–0.47
- 雪花/静止：抽 12 帧算 pixel mean/std + 相邻帧 temporal MAD + 水平/垂直自相关
  （lag 8~128）找块周期

## 三、探针工程军规（血泪换来的六条）

1. **env 门控，默认关**——探针代码留在镜像里零开销，env 一开就亮。
2. **打前备份，锚点唯一**——补丁脚本先 `count(OLD) == 1` 校验，不唯一拒打。
3. **打后 diff 自校验**——difflib 检查"只增不删"，有删行自动回滚备份。
4. **坏了从镜像恢复**——`docker create` 挂旧镜像 `docker cp` 拉纯净文件，
   不手工修运行文件（有一次用正则改文件把函数签名截断了）。
5. **探针输出不依赖被测系统**——per-rank print 而非 logger
   （单 rank logger + 外层 except = 静默故障放大器）。
6. **每完成一个阶段就 `docker commit`**——镜像即存档点，随时可回；
   新生产镜像必须同步更新自愈脚本里的镜像 tag（断电事故的教训）。

## 四、静默回退：查表点普查法

跨型号/新架构卡最常见的性能陷阱：**gfx928 这类型号不在库的厂商白名单里 →
库静默回退通用实现 → 服务能跑但性能低 2–5 倍，且不报错。**

排查法（普查，不是猜）：

1. 列出依赖库里所有**按架构 / 设备名 / 矩阵形状查配置表**的位置
   （源码 grep 架构号、白名单常量、dispatch 表）；
2. 逐一核对目标架构是否落在表内；
3. 表外的，确认回退路径是什么、代价多大，然后补表或显式选路。

配套警惕：**版本口径分裂**。同一平台不同工具读到的版本号可能不一致
（hipconfig 报一个数、运行时库报另一个数、cmake 读后者），版本门判断要以
"实际链接的库"为准。

## 五、性能问题的取证工具箱（社区迁移 + 自研）

先建参照，再动手——三个例子：

- **占空比采样**：GPU 利用率 0.8%、每 67s 只有 2s 在算 → 直接排除"算力不足"；
- **CPU 发射时间 vs GPU Event 时间**：前者 16ms/块、后者 590ms/块 → 排除调度/通信，
  锁定 kernel 执行；
- **分段计时归因**：attn 402ms（68%）/ MLP 74ms / 其余 110ms → 知道该往哪使劲；
  通信与调度合计 <1% → 提前证明"优化通信"是死路，省下几周无效功。

从社区源头帖学来的两件兵器（注明来源，见 §七）：

- **KFD debugfs 三件套**（队列停顿取证）：`rls` / `mqds` / `hqds`——对比
  idle / 健康 / 停顿三态的硬件队列描述符，看 rptr/wptr 差值与错误位。
  注意 `amdgpu_fence_info` 对 KFD 用户队列失明，不能替代。
- **Flight Recorder（飞行记录器）**：同流小 marker kernel + host 提交记录，
  停顿时看"最后退休的 marker"vs"host 已提交到哪"——某社区案例三次捕获全部
  恰好落后 2 个 marker，这个精确 lag 就是"提交超越退休"的量化证据。
  自研的 [slow-op] 序列探针是同族技术的粗粒度版。

## 六、证据分级纪律（写工单/报告的黄金标准）

每个结论分三级标注：**measured（实测）/ inferred（推断）/ 不安全说法**。
例："队列 retirement 停止"在只有一次 HQD 采样、MES buffer 未解码时，应写
"leading interpretation"而非"root cause proven"。

配套两条：

- **变量控制矩阵**：假设逐一测试时，每项注明
  "Rejected = 不是必要触发条件或充分规避，**不代表该组件永远无关**"。
- **"不要先动"清单**：无因果信号前别动 halt_if_hws_hang、vm_fault_stop、
  禁 CWSR/时钟门控这类开关——它们会掩盖小实验。
