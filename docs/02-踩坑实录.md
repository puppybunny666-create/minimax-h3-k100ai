# 02-踩坑实录：三大战役完整复盘

> 每个坑都按"症状 → 定位 → 修法"记录；定位过程的失败分支同样保留，因为它们和结论一样值钱。

## 一、平台不兼容：官方路径全线阵亡（2026-08 下旬）

### 坑 1：torch FSDP2 整体不可用

**症状**：官方 FSDP 推理路径启动即挂——FSDP2 的自定义算子/内部分配/内部流在 DTK 26.04 上
水土不服，进程冻死在加载期。

**修法**：自研 FSDP-lite——绕开 torch FSDP 全部内部机制，参数按 dim-0 分片，逐模块
`all_gather_into_tensor` 到预分配池视图（52 组/步，运行期零分配）；配合本地切片代替
root-scatter（避开 RCCL 加载期死锁）。

**教训**：平台不支持某个"全家桶"时，找到它的最小语义子集自己实现，比硬调快得多。

### 坑 2：RCCL 集合通信死锁家族

同一根因（RCCL 2.22.3 对部分集合通信原语在该驱动栈上不稳定）表现成四种症状，逐一对拍绕过
（对照表见 [01-方案 §二](01-方案.md)）。广播环模拟与原生 all_gather 的输出做了 bit-exact
对拍后才敢上线。

### 坑 3：编码器 device_map 跨卡死锁环

**症状**：26GB 编码器用 `device_map="auto"` 摊到多卡 → 编码 20 秒后全体冻结。

**修法**：编码器单卡驻留（限额钉死一张卡），编码完 offload 回 CPU，再对 rank 做重映射
（rank0 = 无幽灵显存的物理卡）。

## 二、图像质量三连：从雪花屏到灰暗糊

### 坑 4：雪花屏——广播环缺自拷贝

**症状**：画面满屏雪花噪声，不崩、不 NaN、指标全正常。

**定位**：广播环模拟里，本 rank 的数据没先拷进自己的槽位就开广播 → 读到自己槽位里的垃圾。
**修法**：一行 `flat[rank*n:(rank+1)*n].copy_(x)`。

**量化判据**（后来沉淀为通用检测法）：抽 12 帧算 pixel mean/std、相邻帧 temporal MAD、
水平/垂直自相关（lag 8~128）找块周期——雪花/静止画面不再靠人眼抓。

### 坑 5：灰暗糊——耗时最长的主战役

**症状**：视频是灰褐色云雾状色斑，无任何可辨识内容。去噪流程 100% 跑完无报错，
每步 ~30s，一切"看起来正常"。

**排查走廊（全部阴性，每项都是一发定生死的判别实验）**：

| 实验 | 结论 |
|---|---|
| FP32 残差流（48 块 bf16 累积假设） | 与 bf16 分毫不差 → 精度无罪 |
| 时间嵌入器离线复算 | cos 0.9998 → 时间路径完好 |
| RoPE 位置网格验尸 / 分词数 / gate 统计 / 注意力熵 / 装配空洞 | 全部排除 |

**破局线索链**：

1. **换 prompt 判别**：同 seed 下"海滩日落" vs "霓虹夜街红色超跑" → 最终 latent 逐 token
   余弦 **0.9999**——两个截然不同的 prompt 产出同一条视频。**条件链路死了**，
   模型在无条件均值上生成——这就是灰暗糊的本质。
2. **文本链逐级探针**：encoder 输出 → condition_proj → token_refiner 三级 dump，
   前两级与离线参考完全一致，分歧锁定 token_refiner。
3. **变体对拍**：手写 refiner 离线复现，qkv"重排/不重排"两个变体——
   **不重排 = 运行时输出（cos 0.99999）**。运行时用的是原始 checkpoint 张量。
4. **权重对拍定罪**：运行时 qkv 权重分片 vs checkpoint 前 1/8 行——
   **max_abs_diff = 0.000000，逐位一致**。而上游明确断言该 checkpoint 是按头分组的
   qkv 布局，必须重排。
5. **凶手浮出**：自己写的 FSDP-lite 加载捷径——

```python
_direct = (os.environ.get("SGLANG_MM_FSDP_LITE") == "1"
    and weight_loader is not None
    and tuple(full_tensor.shape) == tuple(meta_sharded_param.shape))  # ← DTensor.shape 是全局形状，恒相等！
if weight_loader is not None and not _direct:
    weight_loader(temp_param, full_tensor)   # ← grouped-qkv 按头重排在里面，被短路了
```

捷径永远命中 → 全部 50 层主块 + 2 层 refiner 的 weight_loader 钩子失效 → q/k/v 在错位
权重行上切分 → 注意力"锐利但语义全错" → 跨模态绑定死亡 → 无条件均值 → 灰暗糊。

**修复**：捷径改显式 opt-in（默认关闭），默认走 weight_loader。修复验证全部翻转：
sunset vs car 的 latent 余弦 0.9999 → **0.114**；latent 空间结构指标 +0.0008 → **+0.414**；
画面即刻正常（见本仓库 README 首图）。

**为什么两个月才发现**：所有"自一致"验证（块重放、oracle 对拍、USP 门禁）用的都是
**同一份错权重**——oracle 拿 raw 对 raw，错的俩一致，绿灯全亮。这正是
[04-方法论](04-方法论.md)第一条要解决的。

**灰暗糊的数值签名**（沉淀为通用判据）：病态画面像素 std=9.4（正常 50–70）、
帧间相关 0.41–0.47——"灰暗糊"从此可以量化，不必人眼。

### 坑 6：缩卡时的静默 OOM

**症状**：8 卡缩 4 卡，去噪第一步即崩。**定位**：探针逐级收窄——某 rank 的 OOM 异常被
外层 `except` 吞掉，而 logger 只在 rank0 写文件。**修法**：编码器独占一张可见卡。
**教训**：`except: logger.warning` + 单 rank logger = 静默故障放大器；排障探针要
per-rank print，不吃 logger。

### 坑 7：VAE 显存累积——A/B 对照实锤

**症状**：连续第 2 条必在解码阶段 OOM，且报文里 "PyTorch allocated = 0 bytes"。

**A/B**（连续 3 条同规格请求）：

| 组 | 手段 | 第1条 | 第2条 | 第3条 |
|---|---|---|---|---|
| B | 仅 empty_cache | 36.3G ✅ | 46.6G ❌ | — |
| A | 请求尾下放 CPU + 三连回收 | 36.3G ✅ | 36.3G ✅ | 36.3G ✅ |

根因：decode 阶段把 GPU 副本存进 stage 属性跨请求存活——**活引用不是空闲块**，
empty_cache 无效。

## 三、队列悬案："首条快，后续必慢 2.3 倍"（R1→R12）

**症状**：重启后第一条全速（28 s/it），第二条起 78.7 s/it 且无限持续。

**R9 指纹突破**：劣化 = 每去噪步 3 次**固定相位**巨停顿（块号 28/36/44，均 ≡4 mod 8，
与可疑的 `HIP_DEVICE_MAX_HW_QUEUES=8` 重合），单次停顿量子化 2161–2220ms 并随负载涨到
~5.7s；四 rank 毫秒级同步；RCCL/NCCL 层完全静默 → 指向 kfd/驱动队列调度层。

**R11 求助** → 社区两连击：队列轮转机制假说 + "正确变量名是 `GPU_MAX_HW_QUEUES`（ROCm 生态），
我们设的 `HIP_DEVICE_MAX_HW_QUEUES=8` 可能从未生效"；并检出同族官方案例
（ROCm#6437 gfx1151 队列 retirement 停止 / sglang#33978 MI355X silent hang，缓解均为调低
队列数）。

**R12 实锤**：脚本里两个变量 8/26 不一致、谁生效未知；按同族缓解方案调低队列数 →
全部恢复全速。**驱动级实锤照片**：8 卡同时打印

```text
hycu: Over subscribed runlist, process_count:1, max_proc_per_quantum:13,
      compute_queue_count:30, dqm queue num:28
```

（见 [samples/kernel_log_oversubscription_20260828.jpg](../samples/kernel_log_oversubscription_20260828.jpg)，
配合内核 `mes_v11_0.c` 的 oversubscription_timer 线索，构成向厂商反馈的完整证据链。）

**终版参数**：Q=1 破案 → 9/5 再定标 **Q=4** 固化（健康态 Q=1..4 零性能差异，4 进程×Q4=16
槽 < 单卡 28 槽；Q=4 为共卡场景留缓冲）。注意社区经验"单队列只是 risk reduction not
eradication"——若再现**停顿型**故障，第一嫌疑仍是本族 bug 的深层形态。

**两个月里白折腾的方向**（引以为戒）：代码字节级回滚、源池化、热身、官方规避变量、
iommu 参数（实测重启闭环无差）、分块策略、容器参数……**前期 15 项假设全部排除靠的是
"一次一个变量"的矩阵纪律**，而不是灵感。

## 四、ref2va 十三枪 OOM：mmap 毒化（9/6）

**症状**：ref2va 分区（双塔 DiT 124GB + 完整 63GB 编码器）首跑即连环 OOM，六张卡全试过。

**最干净的矛盾数据**（第十三枪）：同进程数秒内 `mem_get_info` 报 ≥20GiB free，
OOM 报文却是 "0 bytes free"；text_encoder torch 分配仅 0.61GB（63GB/14 shards，
meta 占位 + disk offload）。

**根因**：disk-offload 的 mmap **毒化是进程级地址空间行为**——"0 bytes free"≠物理余量。
毒化进程级 ⇒ 独立进程免疫：同卡独立进程分配 15GB 成功（物理余量 34.4GB）。
**这既是 13 枪 OOM 的答案，也是外部业务能与 H3 同卡共存的科学基础。**

**修复链**：VAE 编码放无 mmap 污染的空卡（VE-GPU 补丁）+ ffprobe 4.4 兼容 + decord。
失败路线也存档：参数级驱逐（hooks 持权重）、`model.to("cpu")` 撞 meta tensor、
hook 拆除两难、换卡加载（加载期 rank 62GB OOM 回滚）。

## 五、明确否决的方向（写下来，防止后人再走）

| 方向 | 否决理由 |
|---|---|
| attn 内核优化 | 块内 attn 占 82%，但其中 FA 本体仅 ~27%；且这里是两次画质事故的案发地——风险>收益，用户拍板关闭并写明重启条件 |
| 官方 fusion backport（名义 1.95×）| 1.95× 是 vs-Diffusers 口径；本侧剩余增量仅 ~25-35s/条（5-7%），kernel 含 Hopper PDL，HIP 移植风险高 |
| GEMM 通用调优 | 17%×47%≈3s/步，投入产出不成比例 |
| HIP graph 捕获 | 步内含 RCCL 集合通信，graph 内通信支持未知 |
| `sched_policy=2`（禁硬件调度） | 社区在 gfx1151 上拒绝此路（prefill 前 page fault）；未测，慎用 |

**教训 4（最重要）：优化的第一课是给"不做什么"写文档。** 关闭一个方向的理由
（风险/收益/重启条件）比打开一个更该留痕。
