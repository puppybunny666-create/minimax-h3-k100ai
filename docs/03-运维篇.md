# 03-运维篇：显存"泄漏"翻案、自愈链与断电复盘

> 生产环境的故事：系统上线之后，真正的考验才开始。

## 一、"显存泄漏"翻案（两次）

### 第一次（9/6，交付前）

ref2va 被怀疑"每条泄漏 ~41GB、必须每 2 条重启一次"。纯净环境复测反转：
**3/3 马拉松（42.3 / 41.2 / 41.2 分钟，波动 <0.1%），GPU5 显存全程一字节不差
（52,409 MiB），GPU4 稳定 18.0–18.2G。** 此前的 OOM 是外部服务部署窗口与生成任务
撞卡的**外因**，不是泄漏。早期"第 3 条 OOM"案例（43.2 / 49.2 分钟 PASS 后）同因。

### 第二次（10-11 月，生产期）

平台方报告"FL2VA 显存泄漏、容器反复重启"。排查推翻：

**真因链**：编排器判闲只看自己队列 → 直连 H3 API 提交的任务不可见 → 120s 宽限到期
SIGKILL → DCU 驱动不回收被杀进程显存（53–55GB 幽灵）→ 重启循环
（最严重一天 44 次分区切换）。

**五阶段实测闭环**（按时间顺序取数，构成完整证据链）：

| 阶段 | 实测 | 结论 |
|---|---|---|
| 空闲基线 | 47–48G × 4 卡 | DIT/VAE 无 CPU 卸载，工作集本来就这么大 |
| 推理峰值 | 57G，四卡均匀 | 正常工作集，非爬升 |
| 完成后回落 | 39–40G | **无泄漏铁证**：回落值低于基线 |
| SIGKILL 后 | 冻结快照 | 幽灵 = 杀时快照，非继续增长 |
| 容器重启 | 全额回收 | 唯一可靠回收手段 |

**方法论要点**：两层的误诊叠加——"工作集大"被当成"泄漏"，"杀进程的驱动残留"被当成
"泄漏证据"。判定泄漏必须回答：**和谁比、采样在哪两个时刻之间、增长是否单调**。

**修复**：编排器补丁——双源判闲（自己的队列 + H3 API `/v1/videos` 在途查询）+
boot 恢复防护。补丁后单任务全程 450s 存活到 completed。

## 二、运维坑清单（每条都是事故换的）

| 坑 | 事实 | 对策 |
|---|---|---|
| 幽灵显存 | DCU 驱动不回收 SIGKILL 进程显存；`/proc` 层面看是冻结快照 | `docker restart` 容器是唯一可靠回收；勿人工 pkill 了事 |
| kfd"存在但失效" | 主机异常后 `/dev/kfd` 节点还在但不可用（`No HIP GPUs are available`） | 强制重建：`docker rm -f <容器> && systemctl restart <服务单元>` |
| 自愈脚本盲区 | 自愈只查 kfd 存在性，覆盖不了"存在但失效" | HARDEN_V1（见 §四） |
| env 覆盖陷阱 | run 脚本里 `export X=${H3_X:-默认值}` 会覆盖 docker exec 注入的同名 `-e` | 外部注入变量统一用约定前缀 |
| 进程名双胞胎 | 服务端进程有两种名字，漏杀一种会占住端口导致起不来 | `pkill -9 -f sgl_diffusion; pkill -9 -f 'sglang serve'` 两条都要 |
| health 假阳性 | 端口通了 ≠ 模型就绪 | 就绪判据 = "Application startup complete" + CPU 静默，勿用日志尺寸阈值 |
| 分区切换窗口 | 切换后服务端口晚 30–40s 才真正可用 | 切换脚本等待 + 提交端重试 |
| 首条 vs 后续 | 曾经"第二条必慢"（见 02-实录 §三） | 队列限额 env 必须常设 |

## 三、断电事故复盘（9/10）

**经过**：两次断电/死机。镜像本身从未丢失（主机上 75 个镜像全在）——但自愈重建的容器
**丢了全部补丁**。

**根因**：自愈脚本里钉死的镜像 tag 是旧版（`final-stable-v3`）。断电 → 容器重建 →
用了旧镜像 → 9/5、9/6 的补丁全部不在（grep 验证补丁标记全 0）。叠加开机风暴引发
kfd 二次失效，雪上加霜。

**修复与铁律**：

1. **每次 `docker commit` 新生产镜像，必须同步修改自愈脚本里的镜像 tag**——
   镜像升级不同步自愈脚本 = 下一次断电自动回滚到旧版本，而且没有任何报错。
2. 离线保险：生产镜像定期 `docker save` 落盘（43GB），`docker load` 即恢复完整生产态
   （含全部补丁；权重本就在镜像外的挂载目录，不受影响）。
3. 镜像链谱系写进文档：`qkv-reorder-fix → … → final-coexist`，每个 tag 对应一个
   已验证的战役节点（见 [01-方案 §四](01-方案.md)）。

## 四、HARDEN_V1：自愈链加固

断电复盘后的加固（自愈脚本尾部追加）：

```text
重建容器后 → health 探活（20 次 × 30s 窗口）
  ├─ 通过 → 结束
  └─ 失败 → 自动强制重建一次（docker rm -f + 服务重启）→ 再探活
```

配合两条就绪判据纪律（见 §一坑清单），自愈链覆盖了"kfd 存在但失效"这一此前
的盲区。修复当晚验证：health ~90s 转绿 + t2va 冒烟 PASS。

## 五、交接即文档

这个系统交接给下一个人（或下一次事故后的自己）靠的是三件套：

1. **运维手册**（一页速览 + 完整坑清单 + 恢复手册 + 故障知识库），
   "贴墙版"只保留日常需要的 15 行；
2. **镜像链 + 离线 tar**（环境整体可复现）；
3. **故障知识库**（每次事故的根因/修复/预防，本文档的大部分条目来自它）。

经验值：交接文档不是"写了就完"，而是每次事故后强制增补——它才会一直是真的。
