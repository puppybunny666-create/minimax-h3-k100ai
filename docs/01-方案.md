# 01-方案：六卡布局、组件账与重建配方

## 一、总体架构

```
浏览器/业务端 ──HTTP──▶ sglang-diffusion serve（容器内，OpenAI 风格 /v1/videos）
                          ├─ DiT 62GB bf16：FSDP-lite 4 卡分片去噪（GPU0-3）+ USP 序列并行
                          ├─ Qwen3VL-32B 文本编码器：29.4GB 连续整块驻留单卡（GPU5）
                          ├─ VAE：解码跨 4 卡 tile 分发（GPU0-3），编码走独立卡（GPU4）
                          └─ 产物 *.mp4（24fps，5–15s，短边锁 768，像素预算恒 ~1.03MP）
```

### 六卡布局（与另一路 LLM 业务共存）

| 卡 | 用途 | 占用 |
|---|---|---|
| GPU0-3 | H3 DiT 去噪分片（FSDP-lite，每卡 1/4 权重） | ~39–41 GB/卡 |
| GPU4 | H3 VAE 常驻家（稳态 10.5G，编码峰 20G）+ 外部 rerank 服务 | 合计 ~18G |
| GPU5 | H3 文本编码器（29.4G **连续整块**）+ 外部 emb/ocr/tts 三件 | 合计 ~52.4G |
| GPU6-7 | 另一路 LLM 业务（不属于本项目） | — |

三条布局铁律（每条都有事故背书）：

1. **编码器需要 29.4GB 连续整块**（mmap 装载）——同卡其他服务必须是碎块分配且留足余量，
   两边"单看都合规"加起来正好爆卡的事故发生过（62.7G 满卡挤死调度器）。
2. **勿乱序 `HIP_VISIBLE_DEVICES`**——实测交换两张卡的映射（如 `0,1,2,3,5,4`）功能全对，
   但去噪慢 2.3 倍（64 vs 28 s/it）：乱序 device 映射打穿 RCCL 拓扑优化，peer 链接退化到 PCIe。
3. **部署前后用 `rocm-smi --showmeminfo vram` 对账**——多项目共卡时这是唯一的共同语言。

## 二、四大组件账

### DiT 去噪（主战场）

- 单步 28 s/it（16:9），其中注意力 ~68%、MLP ~12%、norm/调制 ~18%，**通信与调度合计 <1%**
  ——纯算力瓶颈，软件侧无免费提速（这是用 GPU Event 分段计时实测的，不是猜的）。
- FSDP-lite：参数按 dim-0 分片，逐模块 `all_gather_into_tensor` 到预分配池视图（52 组/步，
  运行期零分配）；torch FSDP2 在 DTK 上加载期即冻死，整体不可用。
- USP 序列并行：自研交换层，广播环模拟 `all_to_all`（原生原语死锁，见 02-踩坑实录）。
- ref2va 慢是架构性的：token 数 T=26160，是 t2va（9440）的 2.8 倍，154 s/it 不是故障。

### Qwen3VL-32B 文本编码器

- t2va/fl2va 用**修剪版（50/64 层）**，29.4GB 整块；ref2va 用完整版 **63GB / 14 shards**
  （disk offload，torch 实际分配仅 0.61GB——meta 占位）。
- `device_map="auto"` 摊多卡 → 编码 20 秒后全体死锁；解法 = 单卡驻留 + 编码完 offload 回 CPU
  + rank 重映射。
- 流水线耗时：单条视频中文本编码 ~11s（对比去噪 393s，占比很小）。

### VAE（解码器/编码器双角色）

- **解码**（t2va/fl2va 出片）：上游 `klvae.py` 内置跨卡 tile 分发 + all_gather 重组，但
  sglang 侧从未注入真实分布式组、解码阶段还是 MAIN_RANK_ONLY。60 行补丁激活：
  解码 105.5s → 27.5s（**3.6×**），端到端 -80~100s。
  无损验证：同 seed 两条视频 mp4 md5 完全一致，ffmpeg 解出 raw rgb24 后
  **383,975,424 字节逐位对比 max=0**（tile 划分不变，SP 只改"哪个 GPU 算哪个 tile"，必然一致）。
- **编码**（fl2va 首帧 / ref2va 参考图视频）：fp32 权重 9.8GB + 激活，峰值 ~15GB，
  走独立空卡（VE-GPU 补丁，规避 mmap 毒化，见 03-运维篇）。
- **显存治理**：解码阶段活引用使每请求 +10GB 累积（`empty_cache` 无效）→
  请求尾 `.to("cpu")` + `empty_cache()` + `ipc_collect()`，A/B 对照三连全过。

### RCCL 通信栈（贯穿全程的暗线）

librccl 2.22.3 在该驱动栈上的四症状四绕法：

| 症状 | 绕法 |
|---|---|
| `all_to_all_single`（带 split sizes）运行期死锁 | 广播环模拟：每 peer 依次 broadcast 进 flat 缓冲，本地切片重排 |
| list 版 `all_gather` 大 payload 死锁 | 换 flat 版 `all_gather_into_tensor` |
| 运行期 `hipMalloc` 与在飞通信触发驱动死锁 | 启动期预分配交换 scratch + 通信器尺寸预热（梯度递增 all_gather 逼出 lazy buffer） |
| ulysses 子组 communicator 运行期死锁 | 子组=全组时改用 WORLD 组 |

每种替代都过了算子级 bit-exact 对拍才上线。HIP graph 捕获曾尝试加速，因步内含 RCCL
集合通信（graph 内需支持通信）而放弃。

## 三、关键环境开关（自研控制面板，30+ 个，节选）

| 开关 | 作用 | 默认 |
|---|---|---|
| `GPU_MAX_HW_QUEUES=4` | 队列限额（劣化根治 + 共卡缓冲） | 必设 |
| `SGLANG_MM_FSDP_LITE=1` | 启用 FSDP-lite 分片 | 必设 |
| `SGLANG_MM_VAE_SP=1` | VAE 跨卡解码（3.6×） | 必设 |
| `SGLANG_MM_VAE_HOME=1` | VAE 常驻家（稳态 10.5G，免重复装卸） | 可选 |
| `SGLANG_MM_REQ_CACHE_CLEAR=1` | 请求尾 VAE 下放 CPU（防累积） | 必设 |
| `SGLANG_MM_LITE_RAW_DIRECT` | 加载直装捷径（**危险**，绕过 weight_loader，灰暗糊元凶） | **必须不开** |
| `SGLANG_MM_WEIGHT_ORACLE` | 权重对拍探针 | 调试 |
| `SGLANG_MM_VAETIME` / `SGLANG_MM_MEMLOG` | 计时/显存记账探针 | 调试 |
| `SGLANG_MM_TEXT_PROBE` | 文本嵌入 shape/mean/std/nan 探针 | 调试 |

约定：全部 env 门控、默认关闭或安全值；探针代码常驻镜像零开销。

## 五、性能优化历程（同一负载的四次测量）

| 时点 | 配置 | t2va 16:9 单条 | 备注 |
|---|---|---|---|
| 9/4 前 | 队列超订未根治 | 首条 ~594s，**后续 1364s**（78.7 s/it） | 两个月悬案 |
| 9/4 | `GPU_MAX_HW_QUEUES=1` | 542–562s，首条=后续 | 马拉松 10/10 |
| 9/5 | Q 定标 4 + VAE SP 解码 | **462–471s（-15%）** | 解码段 118.5s→45.5s |
| — | （评估后放弃）| attn 内核优化、官方 fusion backport | 风险>收益，见 02-实录 §五 |

队列参数结论：健康态下 Q=1..4 零性能差异（4 进程×Q4=16 槽 < 单卡 28 槽静态区）；
劣化触发需要每进程 ≥7（约 52 总需求）才形成 MES 超订——Q=4 是"无代价的抗共卡缓冲"。

## 六、已知限制

- 9:16 竖版慢 2.4 倍：竖版 latent 网格 H/W 交换后 patch 行数 42×48 变化，不利分片（架构性）。
- ref2va 分区切换 ~20 分钟（双塔 187GB 盘 IO），t2va/fl2va ↔ ref2va 二选一。
- HIP graph 捕获未启用（步内含 RCCL 集合通信）；去噪本体占总时长 85%，kernel 调优
  （FA/GEMM ~10-20%）是仅剩的现实空间，需 rocprof 确认瓶颈后再动。
- DCU 驱动不回收 SIGKILL 进程显存（"幽灵显存"）——重启容器是唯一可靠回收方式（见 03-运维篇）。
